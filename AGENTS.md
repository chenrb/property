# Repository Guidelines

## Project Structure & Module Organization

This is a small Django 6.0 project for tracking personal assets, liabilities, and monthly financial review data. The target runtime is Python 3.14. `manage.py` is the main Django entry point. Project settings and root URL configuration live in `config/`. Application code lives under `apps/`: `apps/property/` contains the financial domain models, constants, admin registration, views, migrations, and tests; `apps/core/` contains shared or site-level views and URLs. Shared Django templates live in `templates/`, currently including `templates/index.html`. OpenSpec planning artifacts live in `openspec/`. The local SQLite database is `db.sqlite3`.

## Build, Test, and Development Commands

Create and activate a virtual environment before installing dependencies.

```powershell
python --version
pip install -r requirements.txt
.\env.cmd
python manage.py migrate
python manage.py test
python manage.py runserver
```

`python --version` should report Python 3.14 for the target development runtime. `pip install -r requirements.txt` installs Django and runtime dependencies. `.\env.cmd` sets the local `SECRET_KEY` for Windows shells. `python manage.py migrate` applies database migrations to SQLite. `python manage.py test` runs Django tests across installed apps. `python manage.py runserver` starts the local development server.

## Coding Style & Naming Conventions

Follow `.editorconfig`: 4-space indentation, LF line endings, UTF-8, final newline, and an 80-character line length target. Use Django conventions: models are `PascalCase`, fields and methods are `snake_case`, apps remain lowercase, and migrations are generated by Django. Keep model modules focused by domain, as in `apps/property/models/cash.py`, `investment.py`, and `liability.py`. Prefer explicit imports from app packages, matching the existing `apps.property...` style.

## Testing Guidelines

Tests currently use Django's built-in test framework via `django.test.TestCase`. Place tests in each app's `tests.py` or split into a `tests/` package when a single file becomes crowded. Name test methods with `test_` and describe the behavior being verified, for example `test_debit_card_string_uses_last_four_digits`. Run `python manage.py test` before submitting changes that affect models, views, URLs, or settings.

## Commit & Pull Request Guidelines

Recent history uses short type-prefixed commit subjects such as `feature: ...` and `refactor: ...`; keep that pattern and write the summary in the imperative when practical. Use a focused subject that names the changed area, for example `feature: add liability admin`. Pull requests should include a concise description, test results, migration notes when models change, and screenshots when templates or visible UI change. Link related issues or tasks when available.

## Security & Configuration Tips

`SECRET_KEY` is read from the environment in `config/settings.py`; do not hard-code production secrets. `env.cmd` and ignored `config/local_settings.py` are suitable only for local development. Test commands may use the settings fallback test key when `SECRET_KEY` is absent, but normal development and production runs must provide a real secret. Avoid committing real financial data or personal account details in fixtures, screenshots, or database files.
